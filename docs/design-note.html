memory-harness-chat 設計ノート

対象: memory-harness-chat 0.1.0 ／ 図はクリックで拡大

1. この文書について

memory-harness-chat は、Claude Code のメモリや会話記録から「出典・条件・例外・理由を持つ候補」を抽出し、 ルールやスキルへ可逆的に反映するツールである。前身の memory-harness（Python から Claude Code CLI を外部起動する版）の 検証カーネルを残して補強し、判断の部分を Claude Code のチャットで動く Claude に移した。 本書はその設計と、前身で行った検証の経緯を1枚にまとめたものである。

図はすべてローカルの PlantUML で描画しており、外部サービスへの送信はない。

本書が示せること・示せないこと。 本書が示すのは「機械的に動き、変更を戻せる」こと、そして前身の検証で「実データから既存ルールの大半を再発見できた」ことまでである。 抽出の意味的な正しさと、候補を適用した結果として実タスクの性能が上がるかは、測っていない（10章）。 本版での実データ検証も、本書の時点では行っていない。

2. 解決する問題

会話の中で出た指示（「絵文字は使わない」など）は、メモリや議事メモに自然文のまま残る。 自然文は、Claude が毎回それを守る保証がない。本ツールは自然文から条件・行動・例外・理由を分けて取り出し、 ハーネスが確実に読む形（CLAUDE.md・rules・skills）へ変換する。

図1: 曖昧な記録を、ハーネスが解釈できる形へ移す。これがツールの唯一の目的。

重要なのは「変換して終わり」ではない点である。すべての候補に原文の引用と行番号が付き、 捏造された引用は機械検査で弾かれる。出どころを常に遡れる。

3. 理論的背景（5つの先行研究の応用）

5つの先行研究・先行実装から、それぞれ1つずつ設計を取り入れている。 重み学習や自動進化は採用せず、明示的なバッチ処理・根拠検証・比較評価・可逆な反映だけを応用した。

4. 全体構成

構成の核は判断役と検証役の分離である。候補の抽出と、候補同士の重複・矛盾の照合という「意味の判断」は、 チャットの Claude がその場で行い、結果を run フォルダの JSON ファイルに書く。Python は検証カーネルだけを担い、 原文の凍結と引用の照合、計画と承認の hash 結合、盲検の比較評価、hash 検証つきの適用と復元を行う。 外部から Claude を起動する経路は存在しない。

図3: モジュール構成。Claude とカーネルのやりとりは run フォルダのファイル経由。プロジェクト本体に書くのは transaction.py の apply だけで、evaluate は別コピーで動く。
モジュール役割前身からの変更
cli.py薄い入口。コマンドを対応する関数に渡すだけで、段取りはしない新規
responses.pyResponseFileProvider。応答ファイルの responses[key] を返し、無い key はエラーにする新規
analyze.py依頼書（requests）の生成、応答の検査、引用の照合、候補の安定ID依頼書生成を関数として分離
collect.py入力の列挙、UTF-8 原文と hash の凍結、チャンク化補強（.memory-harness 配下の過去 run を収集しない）
plan.pyREVIEW.md・差分・plan.json の生成、境界検査、承認の hash 結合文言のみ

evaluate.py別コピーでの盲検の比較評価補強（ジャンクション検出の共通化、評価器へ渡す JSON の ASCII 化）
process.py評価器プロセスの起動と停止補強（出力に 16 MiB の上限）

前身から取り除いたもの

Claude CLI を呼び出す claude.py（呼出し・記帳・キャッシュ）、コマンド run・doctor・demo、 モデル名・実行ファイル・呼出回数・金額上限・送信確認の各オプションを削除した。理由は3つある。

  • 前身の検証で見つかった不具合4件のうち2件は CLI 接続の経路にあり、CLI の版が変わるたびに壊れうる部分だった（9章）。
  • サブスクリプションでは金額の計上に意味がなく、その概念自体がコード・文書・設定を複雑にしていた。
  • チャットの Claude は利用者と対話しながら判断できるため、読込の承諾・候補の承認・適用の指示という関門を自然に置ける。

5. 処理の流れ（12工程）

図4: 全体フロー。8番（plan）まではプロジェクトは1バイトも変わらない。書き換えが起きるのは11番（apply）だけで、12番（rollback）で戻せる。4〜5番は errors が無くなるまで繰り返す。

依頼書（requests）

requests --stage extract は、検証側が必要とする入力をそのまま依頼書に書き出す。 チャンク本文・JSON Schema・指示が1つのファイルにまとまるので、Claude は run フォルダの他のファイルを読む必要がない。

図5: requests/extract.json の形。items は検証側が provider に渡す (key, payload, schema) と同じ関数から生成されるため、依頼書と検証の対象が食い違わない。

応答（responses）

チャットの Claude は、依頼書の instructions と response_schema に従って item ごとの応答を書く。 validate は ResponseFileProvider を通してこのファイルを読み、前身と同じ検査（引用の照合・schema との整合）を適用する。 応答の無い key はそのチャンクの error として記録され、complete が false になる（終了コード 3）。

図6: responses/extract.json の形。key は依頼書の item と同じ。チャンクごとに disposition と reason を持ち、候補があれば candidates に並べる。
図7: 候補1件の構造。condition / action / exceptions / rationale / evidence が分離され、すべての項目が原文の行番号まで遡れる。

照合（review）

requests --stage review は候補ペアの依頼書を書き、Claude が全ペアに1件ずつ判定（none / duplicate / conflict / overlap / supersedes）を書く。 relations は要求したペアがすべて判定されているか、conflict に両立不能な具体例が付いているかを検査する。 依頼書と relations には同じ --max-pairs・--review-batch-size を渡す。値が違うとペアの組み方と key が一致しない。

終了コード

コード意味次にすること
0完了次の工程へ
2入力・整合性・操作エラー原因を直して再実行（run は作られない、または変更されない）
3未完了（complete が false）errors に挙がった key の応答だけ直して再実行
130中断途中結果は run に残る
validate は毎回すべてのチャンクを検査し直すが、応答ファイルは残るので、手戻りは直した分だけで済む。 承認と適用の hash 結合は前身と同じで、応答ファイルが後から書き換えられても plan・approve の hash 検査で止まる。

6. 役割分担

この設計の核は役割を混ぜないことにある。意味の判断は AI、検証と実行は機械、採否は人。 AI の出力は必ず機械の検査（引用照合・hash）を通ってからしか先へ進めない。

図8: 3者のやりとり。AI が出したものを機械が締め、読込の承諾・候補の採否・適用の指示は人だけが決める。
役割担当行うこと
判断チャットの Claude依頼書を読んで候補を抽出する。候補ペアの重複・矛盾を判定する。REVIEW.md の要点を利用者に見せる
検証と実行Python カーネル原文を凍結し、引用と行番号を照合する。計画と承認を hash で結ぶ。盲検の比較評価を行う。hash 検証つきで適用・復元する
決定利用者読込を承諾する。候補 ID と理由を選ぶ。適用を指示する

前身との違いは、Claude への入出力が「標準入出力」から「run フォルダのファイル」に変わったことである。 応答ファイルは run に残るので、どの判断がどの根拠から出たかを後から追える。

7. 安全設計（書き込み境界）

実装を読んで確認した実際の挙動である。README の主張ではなく、コードの読解結果を記す。

図9: 触れる場所と触れない場所。プロジェクトへ書けるのは4種だけで、既存ファイルの上書きは構造的に不可能。Claude が読み書きするのは run フォルダの依頼書と応答だけ。
観点実装の実際
ネットワークsocket / urllib / requests の import なし。外部プロセスの起動は evaluate が評価器を呼ぶ経路と、Windows でその停止に使う taskkill だけ

本版への組み替え

前身の検証で残った課題のうち、rule の paths と照合上限は運用パラメータの問題であり、設計の欠陥ではない（10章）。 一方、CLI 接続の経路は「実機でないと気づけない」不具合の温床で、CLI の版に追従し続ける必要があった。 本版はその経路を取り除き、判断をチャットの Claude に、検証をカーネルに、決定を利用者に置く形へ組み替えた。 検証4で有効だった「入力一覧への承諾」は、manifest とスキルの手順として本版に組み込んでいる。

10. 既知の限界

限界1: rule 種別の paths が空になる

検証4で rule 候補103件のうち85件（82.5%）が「paths が空」で適用不可になった。 入力元のルールはほぼ全プロジェクト共通で、特定のフォルダに紐づかない。 ツールは「rule＝パス限定の規約」という前提で作られているため、こうした使い方と噛み合っていない。常時効く方針は claude_md を選ぶ。

図17: 保留が大量発生する構造。常時効く方針は rule ではなく claude_md へ寄せる必要がある。

限界2: 意味照合が候補数の二乗で増える

候補226件では 25,651 ペアになる。既定の照合上限 1,000 ペアでは全体の4%しか照合できない。 候補が3桁になる入力では、上限を大幅に上げるか、入力を分割して複数の run にする必要がある。上限で切れた分は照合済みにはしない。

限界3: 引用の実在は保証するが、意味の忠実さは保証しない

照合は引用文字列の実在と行範囲だけを検査する。抽出された condition / action / rationale が その引用から意味的に導けるかは検査していない。検証4の「誤り11件」はこの隙間から生じている。

限界4: 適用後の性能改善は未測定

前身の検証は「抽出が既存ルールと一致するか」までである。適用した結果として実タスクの遵守率や成果が上がるかは、 独立した課題セットと盲検の評価器を用いたベンチマークが要る。評価器の盲検化と評価の関門化は、そのための前提を整えたものである。

限界5: 判断の品質はチャットの文脈に依存する

本版では、抽出と照合の品質はチャットで使うモデルと、その時点の文脈の長さに依存する。 多数のチャンクを一つのチャットで処理すると文脈が長くなり、後半の応答の品質が落ちうる。入力を分けて複数の run にする方が安定する。 応答ファイルは Claude が書くため、候補が多いと時間もかかる。本版での実データ検証は、本書の時点では行っていない。

結論

前身の 96% の再発見率は、手作業で時間をかけて言語化されたルールに、ツールが1回の実行で追いついたことを意味する。 本版はその検証カーネルを変えずに、壊れやすかった接続経路を取り除き、判断と決定を人の見える場所（チャット）に置いた。 残る課題は運用パラメータの調整（paths の扱い・照合上限・チャンクサイズ）と、性能改善を測るベンチマークの設計である。
